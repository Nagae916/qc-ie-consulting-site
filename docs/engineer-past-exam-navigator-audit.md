# 技術士 経営工学 過去問ナビ監査

- 確認日: 2026-08-09
- 対象: 令和元年度から令和7年度までの過去問126問
- 目的: 過去問から答案の型と通常Knowledgeへ進む導線を整え、未整備Knowledgeと重複候補を把握する

## 1. ナビゲーション方針

過去問ナビでは、年度、問題形式、テーマの3項目だけで問題を絞り込む。各問題では、設問要求を自然な日本語で示し、答案の型、最大5件のキーワード、通常Knowledge、答案例、公式問題へ接続する。

キーワードの定義本文は資格ページへ複製せず、通常Knowledgeを正本とする。対応するKnowledgeがないキーワードは無理にリンクせず、下記backlogで管理する。

## 2. Keyword taxonomy

126問のタグは、既存metadataを書き換えず、分析時に次の6区分へ分ける。

| taxonomy | 対象 | 過去問ナビ・Knowledgeでの扱い |
|---|---|---|
| concept / method | KPI、OEE、SCM、S&OP、FMEA等 | 独立したKnowledge候補。既存Knowledgeを最優先でリンクする |
| objective / issue | 生産性向上、脱炭素、人材育成等 | 解決したい課題・目的。単語ページを量産せず、テーマや複数Knowledgeをつなぐ |
| law / regulation / policy | 下請法、労働安全衛生、消費者保護等 | 一次資料、施行日、更新日を要する参照情報。通常Knowledgeと同列に扱わない |
| source / report | ものづくり白書、国土交通白書、環境白書等 | KnowledgeではなくReferences・出典metadataとして扱う |
| domain / topic | サービス産業、情報セキュリティ等 | 内容の広さに応じてテーマハブ、タグ、複数Knowledgeへの入口にする |
| exam metadata | 設問形式、要求事項、評価項目等 | 技術士試験内の案内にだけ使い、通常Knowledgeへ変換しない |

分類が重なる語は、読者がその語から得たい主目的で決める。人材育成は今回は目的・課題、情報セキュリティは分野、サービス設計は再利用できる設計手法として扱う。法令・白書は出現数が多くてもKnowledge backlogから除外する。

### 表記の正規化

- `KPI管理` / `KPI` は `KPI` に統合して集計する。
- `QMS再構築` / `QMS` は `QMS` に統合して集計する。

- VE / VA / value engineeringは現在の126問のタグにはなく、既存URLの統合判断は行わない。

## 4. 重複候補5組

内容重複率は、frontmatterと記号を除いた本文の文字2-gram Jaccard係数による参考値である。日本語の意味的な重複率ではないため、この値だけで統合を判断しない。inbound internal linksは `content`、`pages`、`src` にある明示的なURL参照数で、ガイド一覧の自動掲載は含まない。

| 候補 | 主な検索意図 | 文字重複率 | inbound links | canonical / sitemap | 正本候補 |
|---|---|---:|---:|---|---|
| `psi` / `psi-management` | 前者は試験学習の短い入門、後者は販売・生産・在庫をつなぐ実務解説 | 11.7% | 0 / 0 | ともに自己canonical、掲載 | `psi-management` |
| `scm` / `supply-chain-management` | 前者は答案で使う全体最適論点、後者はSCMの短い入門 | 7.0% | 48 / 0 | ともに自己canonical、掲載 | `scm` |
| `s-and-op` / `sop` | 前者は経営工学キーワード解説、後者は短い学習ガイド | 7.6% | 19 / 0 | ともに自己canonical、掲載 | `s-and-op` |
| `lcc` / `life-cycle-cost` | 前者は答案向けLCC論点、後者はライフサイクル全体費用の短い入門 | 9.6% | 11 / 0 | ともに自己canonical、掲載 | `lcc` |

アクセスデータがないため、URL削除、redirect、canonical変更、sitemap除外は行わない。統合を検討する際は、検索クエリ、流入、被リンク、本文の意味的差分を確認し、旧URLから正本への301移行計画を作る。

## 5. カード情報優先度とCTA

カードは次の順で表示する。

1. この問題で問われていること
2. 答案の型
3. 答案に使えるキーワードと、理解を深める通常Knowledge 1件
4. 同じ答案型の例
5. 公式問題
6. この問題で示す力

答案の型を最も強いCTAとし、Knowledgeはリンク可能な最大5キーワードのうち代表1件だけをSecondary CTAにする。答案例と公式問題はテキストリンク、評価項目は「この問題で示す力」として最下部の補助情報にする。曖昧な「詳しく見る」は使用しない。

## 6. 表示件数と性能

- 初期表示は8問だけをDOMへ描画し、126問を一括展開しない。
- 未絞り込み時は `126問中 8問を表示` と示す。
- 絞り込み時は `該当する過去問：N問` と示し、9問以上の場合は現在の表示数も併記する。
- 追加表示は8問単位とし、フィルタ変更時に初期8問へ戻す。

## 7. UX簡易評価

- 技術士入口から過去問ナビ: 1遷移
- 年度・問題形式・テーマの絞り込み: ページ遷移なし
- 問われていることの確認: カード内で完結
- 答案の型またはKnowledgeの確認: 追加1遷移
- 公式問題の確認: カードから追加1遷移

特定年度のIII問題について方向性を見る場合、入口から2遷移以内で「設問要求」「答案の型」「キーワード」に到達できる。MVPでは自由記述、答案生成、内部項目表示、重複CTAを置かない。

## 8. main統合前の保守確認

### theme query

126問の既存metadataは `themeTags` に画面表示用の日本語ラベルを持つが、theme専用の安定したIDまたはslugは持たない。そのためMVPのqueryは、日本語ラベルをURLエンコードして保持する。1件だけにIDを追加したり、コンポーネント内に全テーマ分の別名表を重複作成したりせず、126問metadataは変更しない。

将来、表示名変更に強い共有URLが必要になった場合は、theme taxonomyの正本を定義し、安定ID、表示名、旧値の互換規則をまとめて設計する。URL統合や既存queryの互換対応を伴うため、4答案型の整理とは分離した独立タスクとする。

### Desktop表とMobile要約

答案骨子ガイドのDesktop表とMobile要約は、現時点では同じMDX内に手入力しており、単一の構造化データから生成していない。必須Ⅰ、Ⅱ-1、Ⅱ-2、Ⅲの件数、用途、答案構造、注意点は相互に矛盾していないことを確認済みであり、今回のmain統合はブロックしない。

次の「4つの答案の型」監査では、既存の答案型ルール、ワークシート、記入例との正本関係を確認し、Desktop表とMobile表示を同じ構造化データから生成できるかを検討する。全面リライトや新しいデータ構造の追加は、重複削減効果と既存導線への影響を確認してから判断する。
