# Change Policy

## 1. Protected Defaults

次は、現在のユーザー指示に明示的な変更要求がない限り維持する。

- ブランド、ドメイン、メインメッセージ、中心領域。
- 製造業の若手・中堅実務者というメインターゲット。
- 4テーマと、資格を副導線に置く情報設計。
- 6つのコンテンツ形式と初期ケース2件。
- 既存URL、公開記事、機能、検索評価の保全。
- 静的生成・MDX中心、最小限のClient Componentという技術方向。
- 依存関係、CMS、データベース、認証、外部APIを安易に増やさず、APIキーをサーバー側で管理する方針。
- 可読性、モバイル、アクセシビリティ、抑制した演出というデザイン原則。

## 2. 明示的な変更指示

Protected Defaultsを変更できるのは、現在のユーザー指示が対象を明示している場合だけとする。

明示例:

- ブランド名を変更する。
- メインターゲットを変更する。
- 技術士をトップカテゴリーへ戻す。
- 特定URLを変更する。
- CMSや認証を導入する。
- デザイン原則を変更する。

「全体を良くする」「整理する」「モダンにする」「SEOを強化する」「リファクタリングする」等は、Protected Defaults変更の許可とみなさない。

## 3. 変更時の処理

1. 変更対象と明示指示を特定する。
2. 影響するページ、URL、コンポーネント、データ、コンテンツを調査する。
3. 既存方針との差分、移行リスク、戻し方を報告する。
4. 必要なコードと文書を最小差分で変更する。
5. Decision Logへ理由、影響、移行、検証を記録する。
6. lint、型チェック、テスト、ビルド、リンク、主要画面を確認する。

明示指示が明確な場合、古い設定だけを理由に変更を拒否しない。

## 4. サイレント変更の禁止

- 指示されていないブランド、ターゲット、URL、カテゴリー変更。
- 指示されていない依存関係、CMS、データベース、認証の追加。
- 指示されていない記事削除、全面リライト、機能削除。
- 関係のない大規模リファクタリング。
- テスト通過だけを目的とする仕様変更。
- エラーを隠すための機能削除。

## 5. 文書更新

- Goalや成功条件の変更はProject Charterへ反映する。
- 製品判断原則の変更はProduct Principlesへ反映する。
- ナビ、テーマ、ルート責務の変更はInformation Architectureへ反映する。
- メタデータや分類の変更はContent Modelへ反映する。
- 視覚・操作原則の変更はDesign Principlesへ反映する。
- URL変更はURL Migration Policyに従う。
- Protected Defaultsを変える決定はDecision Logへ記録する。

## 6. 回帰確認

- 主要URL、リダイレクト、内部リンク。
- 公開記事とデータの欠落、重複。
- モバイルの読み順、操作、文字切れ。
- アクセシビリティとセキュリティ設定。
- JavaScript量、ビルド出力、既存警告の増減。
- typecheck、lint、テスト、ビルド。

## 7. 変更報告

完了時は、変更したもの、変更しなかったもの、Protected Defaultsへの影響、検証結果、残課題を報告する。
