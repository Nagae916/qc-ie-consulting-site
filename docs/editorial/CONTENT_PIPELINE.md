# Content Pipeline

## 1. 標準フロー

```text
仕事・学習・会話からの気づき
  -> Content Seed
  -> 事実・出典確認
  -> noteドラフト
  -> 再利用できる原則の抽出
  -> N-IE Lab Knowledge
  -> 図解・ツール・ケースとの接続
  -> SNSで入口を作る
  -> 読者反応と更新条件を記録
  -> Knowledgeを更新する
```

この順序は強制ではない。すでに一般化された知識はKnowledgeから作成でき、個人的な背景を公開する価値がなければnoteを省略できる。

## 2. Content Seed

Content Seedには、少なくとも次を記録する。

- 起点となった問い。
- 想定読者と困りごと。
- 仮の中心主張。
- 事実として確認が必要な点。
- 既存コンテンツとの関係。
- note、Knowledge、ケース、ツールのどれが適するか。

機密情報や個人情報はSeedの段階でも残さない。

## 3. 事実・出典確認

一次情報、公的資料、規格、原著に近い資料を優先する。次を確認できない主張は、断定を弱めるか、公開対象から外す。

- 誰が、いつ、どの範囲について示した情報か。
- 最新版か、歴史的資料か。
- 引用と要約の境界が明確か。
- 個人の解釈が混ざっていないか。

## 4. note編集

noteは、導入、問い、考察、具体例、結論を基本とする。中心主張をひとつに絞り、事実と意見を分ける。N-IE Labの記事を短く言い換えただけの原稿にはしない。

## 5. Knowledge抽出

noteまたはRaw Contentから、別の現場でも使える定義、判断軸、フロー、失敗条件を抽出する。既存ページで十分に扱っている場合は、新規Knowledgeを作らず、既存ページの補強候補または内部リンク案として扱う。

## 6. 公開前ゲート

- Protected Defaultsへの影響を確認する。
- 既存URL、タイトル、主要タグ、検索意図の重複を確認する。
- frontmatter、内部リンク、Contentlayer、sitemap、draft除外を確認する。
- typecheck、lint、buildと必要な画面確認を行う。
- Agentの出力は、人がレビューし、専用ブランチとPRを経て公開する。

## 7. 公開後の更新

出典の改訂、法令・規格の更新、前提条件の変化、読者からの誤解、関連ケースの追加を更新の契機とする。更新時は `updatedAt` と適用範囲を見直す。
